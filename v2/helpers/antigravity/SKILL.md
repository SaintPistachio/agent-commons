# Antigravity Helper

Proactively use the included Antigravity allowance for useful bounded portions of current authorized work. When its validated capabilities fit, prefer it for an independent code proposal, analysis, synthesis, comparison, idea exchange or targeted review that Codex would otherwise perform directly. Prefer direct work for trivial tasks, tightly coupled work, or tasks requiring unavailable tools or unaccepted execution. Preserve quality and verification while making productive use of included quota; account for coordination and review work. This integration balances only Antigravity's Gemini and Claude/GPT quota groups. Keep the selected Codex model, effort, permissions, and service tier unchanged.

## Productive use of the included allowance

At natural task boundaries, look for useful work Antigravity can take on with selected context while Codex handles integration, tools or a different independent part. Do not reserve it only for exceptional uncertainty. Use current quota and reset observations to take suitable opportunities when allowance is available, including meaningful second opinions and rough-idea exchanges. Prefer useful AG assignments over doing all suitable reasoning in the main chat by habit. Quota is shared across chats; observations are not reservations or per-call cost estimates.

Each call needs a concrete contribution to the current authorized task. Reuse still-valid results, avoid duplicate reviews and stop an exchange when it adds no new reasoning. Do not create work, run idle prompts, impose a consumption target, repeat completed analyses, increase effort or add model calls solely to drain quota. Select effort for the assignment's requirements. Preserve direct handling of trivial, restricted-data, live-tool and tightly coupled work. Keep all data, permission, quota and paid-credit boundaries below.

For substantive work, actively look first for useful initial research, a first-pass implementation proposal, document synthesis, or focused debugging that Antigravity can take on while Codex handles another independent part. Use it for productive first-pass work as well as second opinions. Give independent assignments distinct contributions and reuse a verified context bundle when they need the same input version. Additional usage must advance the user's task; no mandatory call count or consumption target applies.

## Independent thinking and review

Use when another perspective could improve a decision, develop an idea, expose an error, or resolve meaningful uncertainty, across suitable technical and nontechnical work. Automatically seek independent input when useful; do not require it for every substantial task or duplicate still-valid reviews.

- **Bounce ideas or results:** share rough ideas, hypotheses, or preliminary findings to develop them, challenge assumptions, suggest alternatives, and explore interpretations. Label tentative inputs and invite constructive challenges; ideas need not be polished.
- **Second opinion:** ask for an independent assessment of the question or conclusion, alternatives, and meaningful disagreements. Do not frame Codex's preferred answer as the expected conclusion.
- **Comparison:** supply options and common criteria; ask for tradeoffs, conditions, missing evidence, and a justified preference where supported.
- **Validation review:** supply reasoning, calculations, claims, code, or test evidence to check for errors and unsupported conclusions. Distinguish evidence examined from actions actually performed. Live checks, source verification, and tests remain Codex's responsibility.

For a useful exchange, assess the first response and send a focused follow-up containing only the selected earlier findings, disagreements, and new constraints. Calls do not share conversation history. Use a new prompt/result file for each call, and use `followup` with `-PreviousModel` only for a narrow continuation. For substantive follow-up coding, analysis, or critique, use its actual `coding`, `complex`, or `review` category and optionally `-ModelFamily` to preserve a suitable family. Continue only while the exchange adds useful reasoning or resolves a concrete question; avoid agreement-seeking, repetitive debate, and open-ended model-to-model loops. Agreement is supporting evidence, not proof: Codex reconciles suggestions with requirements and available evidence and owns the final judgment.

Use `explain` for straightforward discussion/comparisons, `coding` for code proposals, `complex` for demanding analysis, and `review` for substantive critiques or validation reviews. Preserve explicit user restrictions on external delegation; this guidance grants no additional data-transfer or execution authority.

Automatically use this mode after Capabilities reports `codex_native_execution.enabled`. The parent may explicitly assign synthetic acceptance before activation. Keep the default reasoning-only assignment behavior compatible. For implementation, supply the authorized workspace/files/effects, exclusions, expected result and verification; the wrapper may gather relevant selected context within that scope and complete edits/checks, without returning after a proposal. Installed plugins are allowed to coexist. Exact owned guard rows remain mandatory; additional reviewed plugin hook rows and source hashes are verified before/after calls. User-installed plugin lifecycle hooks are trusted host extensions, not contained by the Google model tool guard. They may inject setup instructions or maintain their own plugin configuration; do not treat those instructions as permission to broaden the assigned task. The helper uses per-child DO_NOT_TRACK=1 to prevent DAK detached telemetry and identity lookup; no desktop/global preference is changed. The guard's exact loaded command and source hashes are verified before sending selected context. No global hook or permission change is installed. Scratch directories are not an OS security boundary; the tested pre-execution deny guard enforces the no-tool-access contract. Every call checks quota before inference and refreshes it afterward. Both weekly and five-hour caps apply; Argon has an additional weekly cap. Percentages are relative to each group's own allowance, not comparable token budgets. Claude and GPT share one reported group. Unknown/unparseable quota blocks inference. On quota exhaustion the helper refreshes once and returns control to Codex; choose a suitable eligible alternative or continue directly. Never loop on exhausted quota, buy credits, or schedule polling.

Timeout errors preserve `TIMEOUT` and identify initialization, inference, or process-exit stage, submission state, run/process IDs, timing and explicit unavailable usage/quota. Run-local diagnostics exclude prompts, raw responses and stderr. A submitted request without a terminal result is ambiguous and must not be silently replayed. Ordinary `Run` waits until completion using the supported CLI `--print-timeout 0`; elapsed time or a quiet period alone never terminates a submitted request. `-TimeoutSeconds` defaults to ten minutes and sets the quiet-warning interval. Use `-HardDeadline` with that value only when the parent deliberately requests an absolute ceiling. Startup, blocked pipe submission, post-result cleanup and synthetic checks retain separate bounded controls. Authentication errors require restoring the existing official CLI sign-in, not copying credentials or introducing API billing. ## Setup and recovery

Self-updates remain enabled. On `Run`, CLI-only version/hash drift from an existing passed acceptance triggers one automatic synthetic revalidation before the original prompt is read or submitted. If the CLI replaces itself during initial version discovery, one metadata-only reacquisition is allowed while agent and implementation identities remain unchanged. Repeated changes stop safely. A Windows candidate must have a valid Google LLC Authenticode signature. The same deny-all positive control and restricted tasks in both included quota groups must pass. Candidate CLI, agent, and implementation identities must stay unchanged throughout validation and before task submission. Only then may the helper atomically replace acceptance, refresh controls/catalog/quota, and continue the original invocation. No already-submitted task is replayed.

Revalidation is serialized by a process-released file lock; concurrent callers reuse a successful acceptance. Lock waiting is bounded to 900 seconds, and each automatic probe model call is capped at the smaller of `-TimeoutSeconds` and 180 seconds. This validation phase adds time before the original task. It does not make ordinary task waiting finite. `Status` reports activation without starting a probe. Missing/invalid acceptance, helper or agent edits, and failed/interrupted validation require explicit recovery. Failed candidates are recorded so subsequent tasks do not repeatedly consume quota trying the same candidate; changing CLI identity permits a new attempt.

`-Action Probe` runs only built-in synthetic tasks to validate controls and both quota groups; it does not accept a private prompt. It shares the validation lock and is the explicit recovery path after a failed/interrupted attempt or reviewed helper/agent changes. Installation, acceptance receipts, backups, and rollback are documented in the task delivery report. Never edit a receipt to pretend a failed check passed. Authentication, quota, signature, protocol, guard, or identity-stability failures still block the original prompt.

## Activity and quiet-task inspection

The helper emits the run ID and process ID at startup and saves a redacted `activity.json` in its owned scratch run. Use `-Action Activity -RunId '<known run ID>'` for a metadata-only check; this sends no model prompt, performs no provider request, and does not interrupt or replay the task. Keep the visible wrapper active and attached while the ordinary call runs; do not detach a monitor or start a scheduled job.

Distinguish a successful terminal result, an established failure, an ended process without a terminal result, fresh meaningful progress, quiet running, and stale/unconfirmed observation. The owned observer records process liveness and observation time separately from meaningful model progress. Repeated status/connection heartbeats and mere process presence do not prove useful work. A quiet task stays running and receives a warning; silence is not a failure or an automatic cancellation trigger. Inspect metadata and available safe evidence before concluding what happened.

Do not inject “status?” as another prompt to a busy model. No supported in-flight provider progress-query API is established here, and another prompt could queue or change work. An unconfirmed/stale observation is not permission to resubmit. User cancellation, an explicit hard deadline, actual stream failure/process exit, tool violations or identity/guard failures retain their existing handling. Candidate assessment remains one combination within120seconds; genuine acceptance and CLI-update revalidation remain bounded synthetic work.
